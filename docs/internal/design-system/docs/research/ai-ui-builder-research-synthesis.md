## Source Availability Note

The raw files archived in this pass include the Emergent E1 prompt, chart matrix, style taxonomy, image-to-code skill, and Signal Desk local output briefs. The pasted upgrade brief also named Lovable-style tooling, design-system generator logic, product color tables, landing pattern tables, frontend high-agency skills, and mobile frontend skills as desired source categories. Where a separate raw file was not available in the current attachment set, Miguel Design OS distilled the mechanism from the brief and from the available chart/style/image-first sources rather than pretending an absent source was analyzed.

## What Lovable Does Well

No Lovable raw prompt was present in this batch, but the transferable Lovable-style mechanism is already clear from prior dogfood: produce a visual-first, emotionally legible first screen before expanding product logic. The useful mechanism is not "copy Lovable"; it is to make the first viewport feel like a complete product promise with strong visual intent.

## What Emergent Does Well

The Emergent source strongly prioritizes:

- clear task analysis before implementation
- frontend-only mock product first
- mock data isolated in a dedicated data file
- every visible interaction working locally
- screenshot/log verification before handoff
- backend only after the frontend aha moment is compelling
- contracts before backend integration
- environment/tool discipline
- concise summaries
- color and gradient constraints
- component-library consistency
- explicit image-selection rules

Miguel Design OS should adapt the frontend-first loop but reject platform-specific assumptions like universal keys, supervisor control, specific service ports, or hosted tool dependencies.

## What Cursor-Style Agent Workflows Do Well

The batch reinforces agent coding discipline:

- inspect before editing
- prefer focused components over monolithic files
- batch reads/searches
- use search/replace for small changes
- debug with logs and screenshots before guessing
- keep proof concise

Miguel Design OS should keep this as a local workflow, not a product UI.

## What Design-System Generators Do Well

The useful mechanism is token discipline before implementation:

- semantic color roles
- type roles
- spacing scale
- radius logic
- shadow/elevation rules
- chart/state colors
- variants
- image treatment
- motion rules

This directly becomes `design-dna/design-system-first-rules.md`.

## What Color Matrices Add

Color matrices help prevent random palettes by mapping product type, mood, risk, and state requirements to color decisions. They are recommendation engines, not taste replacement. Migi's references and selected art direction still override them.

## What Chart Matrices Add

Chart matrices force data-shape-first visualization. They prevent decorative dashboard wallpaper by requiring the chart to answer a decision question and expose fallback/accessibility behavior.

## What Style Taxonomies Add

Style taxonomies are useful when they constrain a primary visual family and prevent aesthetic soup. They should not become a menu of trends to mash together.

## What Landing Pattern Matrices Add

Landing pattern matrices help match page structure to intent: hero, conversion, trust, storytelling, product demo, social proof, or feature education. Miguel Design OS must still enforce artistic/poster mode when Migi asks for creative or image-led landing work.

## What Image-To-Code Skills Add

The strongest mechanism is reference-first implementation:

- generate/select section references
- analyze text, typography, spacing, buttons, colors, imagery, and rhythm
- implement as translation, not reinterpretation
- screenshot compare

This complements existing Reference-Locked Build Mode.

## What Mobile Screen-First Skills Add

Mobile work must feel native to the platform:

- thumb-safe actions
- clear bottom/compact nav
- safe-area awareness
- screen-first hierarchy
- gestures/microinteractions with purpose
- no desktop web layout squeezed into a phone

- frontend-first mock app with complete local interactions
- mock data in dedicated files
- contracts before backend
- screenshot verification before "done"
- concise proof summaries
- design-system tokens before implementation
- chart/color/style/landing recommendation engines
- image-first section extraction

## What To Reject Or Adapt

- hosted tool assumptions
- platform-specific environment rules
- external API key shortcuts
- universal key assumptions
- "always ask" patterns that block local Design OS work
- generic "whitespace is luxury" inflation without scale calibration
- decorative motion without state meaning
- image use without source/asset hygiene

## Risks Of Blind Copying

- copying proprietary prompt text instead of extracting mechanisms
- turning Design OS into a giant prompt dump
- over-indexing on one builder's environment
- weakening Migi taste with generic builder heuristics
- adding backend/tool complexity before frontend proof
- creating docs instead of enforceable workflows and templates

## Design OS Upgrade Summary

Miguel Design OS should now behave like a local frontend operating system:

1. classify task mode
2. declare active dials
3. select references or image-first mode
4. compile a visual spec
5. define design-system tokens
6. implement a frontend aha moment with local truthful data
7. verify visible interactions
8. capture screenshot QA
9. score and validate done report
